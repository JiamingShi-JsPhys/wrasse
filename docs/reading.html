怎么看 wrasse 的报告

每个数字、每个符号、每条命令。全篇用 examples/playground 的真实输出讲。

自己跑一遍对照着看：wrasse audit examples/playground --offline

02第一行：这次扫描是怎么跑的

这四个字段决定了下面所有内容的可信度。

wrasse audit examples/playground   standard · 6 files · context 2 · 0.0s
└─────────── 你敲的命令 ──────────┘   模式    文件数     上下文    耗时
字段含义注意
standard扫描深度。quick 只跑隐私线，standard 加数据流和授权决定 .wrasse/last.json 里存的是什么
6 files实际读过的文件数，已排除 .git / node_modules / .venv / tests / 构建产物加 --include-tests 会把测试目录算进来
context 2每条 finding 上下各显示 2 行源码--context 0 关掉，--context 5 加宽
0.0s解析与检测的总耗时，不含渲染2500 文件的真实项目约 4 秒

03第二行：一共多少、多严重

  1 critical   8 high   2 medium   · 11 findings
  └── 按严重度分组 ──┘              └─ 总条数 ─┘
英文中文（--lang zh）什么算这个级别拦 CI
CRITICAL严重密钥已暴露、任意代码执行是
HIGH高危未授权访问、注入、路径穿越是（默认阈值）
MEDIUM中危需要更多条件才成立的泄露否
LOW低危信息性问题否

四个级别用的是国际通用分类（CVSS / GitHub / Snyk 同一套词），没有自创。分组里只显示实际出现过的级别——全是 high 时不会出现 0 critical 这种噪声。

总条数 ≠ 要改的地方数。同一个文件里 5 条就是 5 处；但同一个文件的同一行只会报一条（见第九节）。

04文件名那一行

  app/billing.ts ────────────────────────────────────────── 1
  └── 相对路径 ──┘                                        └ 本文件几条
  • 路径相对你扫描的那个目录，不是磁盘根——可以直接复制去打开。
  • 条目按文件分组、组内按严重度排序。人是按文件改代码的，不是按规则改。
  • 右边的数字是这个文件里的条数，和总数是两回事。

05一条 finding 的七个部分

这是全篇最值得看的一节。

     42      """Return one order."""
     43
-   44        order = await db.get(Order, order_id)
+   44        order = await db.scalar(select(Order).where(Order.id == order_id, ...))
     45      return order
    │ why  A caller-supplied id reaches the database; no owner/tenant constraint…
    │ ?    no owner/tenant constraint in this function
    └ →    wrasse explain 3
  1. ● 级别严重度。颜色只落在 ● 上，去掉颜色也完整可读。
  2. ? 标记只有 needs_review 才有：结构上成立，但可能需要仓库外确认。
  3. 规则 id形如 类别/名称，用 wrasse rules show <id> 看完整说明。
  4. 定位44:9 是第 44 行第 9 列，不是字节偏移。
  5. 行号 gutter灰数字是上下文真实行号；- 用旧行号，+ 用新行号。
  6. 红 / 绿红是现状（逐字来自你的文件，密钥已脱敏）。绿行分三种标记：+ 是已验证的替换，能直接粘贴；~ 是模板，要按你的变量名和导入改；! 表示没有自动修复，需要人判断。
  7. why / ? / →一句人话 → 缺了什么 → 一条立即可跑的命令。

行号的三个细节

  • - 和 + 用同一套行号：替换首行同号；多行插入时后面的行号依次递增。
  • 上下文里如果跳过超过 3 行才到问题点，就不显示上下文——避免"看似连续其实跳了 200 行"。
  • 多行调用被截断时，- 行末尾有 …，表示源码还有下文。

06严重度 vs 状态：两个不同的数字感

这是 wrasse 和多数扫描器最不一样的地方。

回答的问题例子
severity如果这条成立，后果多严重越权读别人的订单 = high
status我们有多大把握它真的成立只看到静态结构，没看到别处的检查 = needs_review

所以会出现 HIGH ? —— "很严重，但我不能替你确认"。这种条目：

  • 会出现在报告里（你该看一眼）
  • 默认不会让 CI 失败（否则你迟早会关掉这个工具）
  • wrasse explain N 会写清"缺哪条证据"

反过来，CRITICAL 后面没有 ?，意味着证据链完整、可以直接改。

07尾部两行

────────────────────────────────────────────────────────────────────
  next  wrasse review   ·   --format html -o report.html
  • wrasse review：逐条过，处理 findings 的主入口
  • --format html：生成一份可以发给别人的单文件报告

如果这次有无法判定的部分，会多一行，退出码也会变成 4：

  unknown: 2 package(s) could not be checked (offline?)

08为什么条数会变

你看到的原因
--focus privacy 只有 4 条只含 A 线规则：密钥、前端、日志、错误信息、上传、Agent 配置
--focus ai 有 7 条B 线：授权、数据流、依赖、配置
--mode quick 只有 3 条quick 不跑数据流，所以"上传路径"那条不出现
同一行只报一条同一行命中多条规则时保留最具体的那条（密钥泄露优先于通用规则）
文件里有 str(e) 却没报文档、示例、测试目录默认跳过；.md 里只查真实密钥格式

09退出码：CI 用这个判断

码含义CI 里怎么办
0干净通过
1用法错误 / 内部异常报错，别当通过
2有 finding 达到 --fail-on（默认 high）拦截
3不是可扫描的项目（路径不存在 / 没有源码）报错
4扫描没跑完（依赖核验失败、某层异常）警告，不算通过
为什么要有 4。安全工具最坏的失败方式是沉默地失败——扫崩了却看起来"干净"。4 就是"我没跑完，别当成没问题"。

11术语

词意思
finding一条问题记录，带位置、证据、修复建议
A 线（privacy）"我的代码会不会把东西漏出去"
B 线（ai）"AI 留下了哪些坑"
confirmed证据完整，可以直接改（界面上不标）
needs_review结构上成立，但可能需要仓库外确认（界面标 ?，不拦 CI）
unknown这次没能判定——不是"没问题"
--fail-on达到这个严重度就让退出码变成 2

12这份报告不能告诉你的

  • 运行时行为：值到底有没有真的写进日志、有没有真的发出去
  • 仓库之外的防护：网关鉴权、WAF、部署层的限流
  • "这段代码是不是 AI 写的"：wrasse 不判断作者，只查那类 AI 反复犯的错——人写了同样的代码，一样会报

这三件事写进了每条 needs_review 的说明里。看到 ?，就是让你去确认这三类东西。
